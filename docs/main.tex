\section{Introducción}

La idea de crear una apliación web de crucigramas surgió mientras estaba preparando la teoría de
CBD. En los temas había muchas palabras y conceptos que podían sintetizarse perfectamente
en una definición. Quería hacer una herramienta que me fuese útil para estudiar y que sirviese
como proyecto para la asignatura.

El stack tecnológico Mongo y ElasticSearch era una buena elección para implementar este
pasatiempo. Los crucigramas se pueden representar en un simple docuemento. La cuadrícula es una
lista de listas que no soportan las BBDD relacionales. 

En el trabajo se han cubierto los siguientes puntos:

\begin{itemize}
	\item Modelar el dominio del problema a un documento en MongoDB
	\item Explorar los tipos de datos que MongoDB ofrece listas, objetos, propiedades sin definir...
	\item Explorar el motor de búsqueda de ElasticSearch
	\item Hacer una aplicación web de un crucigrama que un usuario pueda jugar
\end{itemize}

De todos esos puntos se han implementado con éxito, la interfaz está hecha en React
y la API está hecha en Express, el modelo de datos exprime al máximo las ventajas de
los documentos de Mongo y se ha implementado un buscador de palabras en un diccionario
utilizando ElasticSearch.

\section{Crucigrama}

Para poner en contexto al que no esté familiarizado con este juego.
El crucigrama es un pasatiempo donde tienes que introducir palabras
en una cuadrícula siguiendo las pistas proporcionadas en horizontal y en
vertical por el crucigramista.

Aunque no te sepas todas las palabras puedes llegar a resolver el crucigrama
rellenando otras pistas. Puede que al principio sea complicado y
consultes muchas palabras, pero conforme vas haciendo más pasatiempos te vuelves
más experto.

Por este motivo es un crucigrama divertido, te expones diariamente a un reto 
intelectual, una oportunidad de aprender palabras que desconocías.

De hecho, en Estados Unidos publican diariamente en el periódico
1 crucigrama. Los del lunes son los más sencillos y son pequeños 11 x 11,
los domingos son muy complicados siendo más grandes 21 x 21 y con pistas
más crípticas.

Hay todo un gremio especializado en hacer crucigramas, ya que hacer un buen
crucigrama es muy complicado. Hay que tener en cuenta varios factores como la simetría
de la cuadrícula, la calidad de las pistas, el tema del crucigrama.

En la dos secciones posteriores vamos a hablar de los dos elementos elementales que 
tiene que tener un crucigrama:

\begin{itemize}
	\item Cuadrícula
	\item Pistas
\end{itemize}

\subsection{Cuadrícula}

La cuadrícula es donde podemos introducir la solución del crucigrama. Distinguimos
dos tipos de celdas:

\begin{itemize}
	\item Las celdas negras, bloques...
	\item Las celdas blancas
\end{itemize}

En las celdas negras no se puede escribir nada y sirven para delimitar
la longitud de las palabras. Los crucigramistas, suelen jugar con los bloques
para crear sus crucigramas. Pueden ponerlas por conveniencia para separar
palabras o por simple estética. Dependiendo donde esten situadas, el
crucigrama tendrá más o menos palabras.

No obstante, en las celdas blancas se introducen respuestas a las pistas. 
Además, si nos fijamos en el crucigrama de la figura \ref{fig:americanXword},
podemos ver que algunas celdas tienen numeración. Esto tiene que ver con la
forma de dar pistas en el crucigrama.

Hay dos variantes para dar las pistas, enumerar la celdas como en la figura
\ref{fig:americanXword} y numerar las filas y las columnas de la
figura \ref{fig:xwordESP}.

\subsection{Pistas} \label{sec:pistas}

Un crucigrama está formado por palabras en vertical y en horizontal.

Existen dos formas para hacer referencia a las pistas en la cuadrícula.

\begin{itemize}
	\item Coordenadas: Se numeran las filas y las columnas del crucigrama. Por cada palabra
	que haya en una fila o en una columna se añade a la lista de pistas horizontales o
	verticales en el número que le corresponda. Por ejemplo en la figura \ref{fig:xwordESP}
	la tercera fila tiene 2 palabras, por lo que en las pistas horizontales el número 3
	tiene 2 pistas separadas por puntos.
	\item Numeración de casillas: Se numeran las celdas que empiecen una
	palabra. Puede ver más detalles de la numeración de las celdas en la sección
	\ref{sec:algo}.
\end{itemize}


\section{Modelo de datos}

Si analizamos detenidamente un crucigrama distinguimos 3 elementos básicos:

\begin{itemize}
	\item La cuadrícula
	\item La solución
	\item Las pistas
\end{itemize}

\subsection{Cuadrícula}

Si observamos la figura \ref{fig:americanXword} las celdas están dispuestas en filas
y columnas.

Es sensato pensar en modelar este objeto con una estructura de datos muy utilizado
en el software, una lista. Como tiene coordenadas vamos a utilizar
una lista para guardar las celdas de una fila, por lo que habrá tantos elementos
en la lista como filas haya en la cuadrícula.

Para representar las columnas de la cuadrícula utilizamos otra lista para almacenar
las posiciones de la celda y sus atributos.

Una cuadrícula será válida si cada fila tiene el mismo número de celdas. En la figura
\ref{fig:datamodel} podemos ver la relación de un cuadrícula con sus celdas.

\subsection{Celdas} 

Dentro de una cuadrícula nos encontramos como ya se ha comentados dos tipos de celdas
blancas y negras. El tipo de dato adecuado para modelar este hecho es un atributo
Booleano. Ahora hay que pensar en la semántica de esos dos estados, si este atributo
es verdadero la celda será negra y en caso contrario será blanca.

En la figura \ref{fig:datamodel} el atributo \verb*|dark| indica el estado de una celda.

Otro elemento crucial a representar de las celdas es su solución. Por simplicidad
todas las celdas tendrá un carácter solución. Más tarde esto nos será útil para
calcular la solución fácilmente si no hacemos distinciones de celdas.

En figura \ref{fig:datamodel} en la clase \textit{Cell} este atributo se llama
\verb*|solution| y es de tipo cadena.

A estas alturas ya sabemos como representar la cuadrícula y podemos introducir
las soluciones pero ¿Cómo vamos a resolver el crucigrama si no hay referencias
a las pistas en la cuadrícula?.

A estas alturas tenemos que elegir la estrategia a implementar para hacer referencia
a las pistas ya previamente explicada en la sección \ref{sec:pistas}. La estrategia
que he elegido ha sido la de numerar las casillas.

Es bastante intuitivo para los usuarios que resuelven el crucigrama. Cada celda
numerada es una palabra y al contrario que la estrategia de coordenadas en el que
una fila contiene una o más palabras separadas por puntos.
 
Con esta estrategia en mente es importante destacar que no todas las celdas están
numeradas. Por ejemplo si nos fijamos en la figura \ref{fig:xwordNYT}, la celda de 
la tercera fila y la segunda columna no tiene ningún número asignado. Esto se debe
a que esa celda ya pertenece a la palabra 1 en vertical y a la palabra 6 en horizontal.

Con todo esto en mente la etiqueta o número de una celda será un atributo opcional.
En el modelo de datos de la figura \ref{fig:datamodel} este atributo se llama
\verb*|label|.

Estos serían los atributos básicos que tendría nuestro modelo. Ahora bien, si
queremos que el usuario no se pierda mientras está resolviendo una pista, podemos
iluminar las casillas que corresponden a la pista en la que está concentrado
como podemos ver en la figura \ref{fig:xwordNYT} del crucigrama del New York Times.

Con esta nueva característica tenemos que expandir el modelo y añadir más atributos.

Podemos modelar esto con dos atributos opcionales que tendrán una etiqueta de la
palabra horizontal y vertical a la que pertenecen. Estos dos atributos opcionales
no pueden ser simultáneamente nulos ya que una celda siempre pertenece al menos a
una palabra del crucigrama ya sea en horizontal o en vertical. No obstante, puede
darse la situación de que una celda no pueda pertenezca a una palabra en horizontal
o viceversa.

Los atributos opcionales serán cadenas de texto, la primera parte de la cadena es
el número de la palabra a la que pertenecen y la segunda parte de la cadena es una
etiqueta que identifica si pertenece a una palabra en horizontal o en vertical,
\verb*|<número><A/D>| (Horizontal en inglés es Across y Vertical en inglés es Down).

Estos dos atributos opcionales en el modelo de datos de la figura \ref{fig:datamodel}
se llaman \verb*|across| si la celda pertenece a una palabra en horizontal y \verb*|down|
si la celda pertenece a una palabra en vertical.

La cuadrícula modelada de la figura \ref{fig:xwordNYT} como un documento en JSON
tendría el siguiente aspecto (Se ha modelado la primera fila de la cuadrícula por brevedad;
La solución a la palabra 1 en horizontal es VIP):

\begin{verbatim}
[
  [
   { 
   	dark: true
   	solution: "."
   },
   {
   	dark: false,
   	solution: "V",
   	label: "1",
   	across: "1A",
   	down: "1D" 
   },
   {
   	dark: false,
   	solution: "I",
   	label: "2",
   	across: "1A",
   	down: "2D"
   },
   {
   	dark: false,
   	solution: "P",
   	label: "3",
   	across: "1A",
   	down: "3D"
   },
  ],
  ...,
]
\end{verbatim}

\subsection{Pistas}

Otra parte fundamental a modelar del crucigrama son las pistas. Como vemos
en la figura \ref{fig:xwordNYT}, situada a la derecha de la cuadrícula podemos
ver dos columnas con pistas en horizontal y en vertical (Across y Down).

Siguiendo esta misa filosofía, podemos pensar en una pista como un objeto
con dos atributos que contengan una lista de las pistas en horizontal y en
vertical.

En el modelo conceptual sería simplemente una lista con pistas sin clasificar,
pero como en un documento tenemos la facilidad de añadir atributos vamos a 
distinguir las pistas y no ponerlas en la misma lista.

Cada pista del crucigrama debe de tener dos atributos, la referencia de la pista
en el crucigrama y el texto de la pista. Estos dos atributos nuevamente serán cadenas
de texto.

En el modelo de datos de la figura  \ref{fig:xwordNYT} esto atributos se llaman
\verb*|label| y \verb*|hint| respectivamente.

El documento que modela a las pistas del crucigrama  de la figura \ref{fig:xwordNYT}
se tendría el siguiente aspecto:

\begin{verbatim}
	{
	  "across": [
	    {
	      "label": "1A",
	      "hint": "Someone who might have a special line to the entrance"
	    },
	    ...
	  ]
	  "down": [
	    {
	      "label":"1D",
	      "hint": "Physicist for whom an electrical measurement is named"
	    },
	    ...
	  ]
	}
\end{verbatim}

\subsection{Crucigrama}

Con la cuadrícula, la solución y las pistas ya tenemos un crucigrama funcional que podemos
representar en un documento. 

Aunque antes de eso podemos añadirle más información y semántica al modelo.

Como los crucigramas se publican diariamente añadimos un atributo de tipo fecha. Además
vamos a imponer como regla de negocio que no puede más de un crucigrama publicado en un
día.

También añadimos al modelo 3 atributos derivados, el número de palabras horizontales,
el número de palabras verticales y el número total de palabras que serán calculados.

Todos estos atributos están en la clase \textit{Crossword} de la figura \ref{fig:datamodel}.

El documento final del crucigrama de la figura \ref{fig:xwordNYT} tendría el siguiente
aspecto con todos los documentos ensamblados. Para no repetir los documentos anteriores
se ha puesto una elipsis:

\begin{verbatim}
	{
		"date": { "$date": "2024-06-24T00:00:00.000Z" },
		"numRows": 5,
		"numCols": 5,
		"numWords": 10,
		"numWordsAcross": 5,
		"numWordsDown": 5,
		"crossword": [[...],...]
		"clues": { across: [...], down: [...] }
	}
\end{verbatim}

\section{Marco de trabajo}

Con el modelo de datos terminado ya tenemos un documento que podemos pasar a 
EJSON \cite{EJSON} (archivo compatible con el RFC 8259 en el que se especifican
en JSON los tipos de datos de MongoDB).

Hay un problema con el modelo planteado, es bastante largo como para que alguien
escriba el JSON manualmente.

Por esta razón se ha desarrollado el marco del proyecto un script que transforma
plantilla de un crucigrama en un formato personalizado a un un documento plantilla
EJSON (Paso 1 de la figura \ref{fig:framework}).

Posteriormente rellenaremos la plantilla con las pistas y finalmente importaremos
el documento a nuestra BBDD (Paso 2 de la figura \ref{fig:framework}).

  
\begin{figure}[t]
	\centering
	\includegraphics[width=\linewidth]{img/framework}
	\caption{Transformación de la plantilla personalizada de la cuadrícula a una platilla
		EJSON que puede leer MongoDB}
	\label{fig:framework}
\end{figure}

La plantilla personalizada para representar un crucigrama es el de la página
\textit{Words Up?} \cite{wordsUp} que tiene un gran librería de crucigramas.

El formato propuesto por la página es el siguiente:

\begin{itemize}
	\item Es un archivo de texto corriente.
	\item Las bloques se representan con un punto.
	\item Las celdas en blanco se representan con un interrogante.
	\item El número de filas del crucigrama es el número de líneas del archivo de texto.
	\item El número de columnas del crucigrama es la longitud de caracteres de una
	línea. La longitud debe ser consistente en todas las líneas del crucigrama. Es
	decir todas las líneas deben tener la misma longitud de caracteres.
	\item El saldo de línea \verb*|\n| o \verb*|\r\n| es la terminación
	de una fila y el comienzo de la siguiente.
	\item Cualquier carácter que no sea un punto, un interrogante o un salto de línea
	no cumple con el formato esperado del archivo de texto.
	\item No pueden haber líneas en blanco.
\end{itemize}

Por ejemplo en la figura \ref{fig:xwordCustomFormat} podemos ver el formato de archivo
propuesto. 

\begin{figure}[t]
	\centering
	\includegraphics[width=0.7\linewidth]{img/formato.png}
	\caption{A la izquierda un crucigrama con 5 filas y 5 columnas.
		A la derecha la representación del crucigrama en un archivo de texto}
	\label{fig:xwordCustomFormat}
\end{figure}

Este formato facilita la creación de plantillas, siendo la alternativa de escribir el
EJSON menos legible y mucho más verboso.

Una vez ya tenemos la plantilla de la cuadrícula escrita le damos la cuadrícula al
script y el programa se encarga de crearnos la plantilla en EJSON \cite{EJSON}.

Ya con el archivo en EJSON creado, tiene que escribir la solución del crucigrama en
la cuadrícula, que es simplemente rellenar donde ponga \verb*|<SOLUTION>| el carácter 
solución de la celda correspondiente. Después en la sección \verb*|clues| tiene que rellenar 
las pistas horizontales y verticales. 

Es importante mencionar que antes de que importe el EJON a MongoDB tiene que poner la
parte de la hora a cero \verb*|00:00:00.000Z|, si no lo hace el front no funcionará: 

\begin{verbatim}
	"date": { "$date": "2024-06-22T00:00:00.000Z" }
	...
\end{verbatim}

Una vez que haya hecho las modificaciones pertinentes a la plantilla ya puede importar el
EJSON en la instancia de MongoDB.

Para ejecutar el script por favor consulte el \verb*|README| del repositorio \cite{repositorio}
o el Anexo \ref{sec:Anexo} de este documento.


\section{Tecnologías}

\subsection{Express}

Para que la aplicación sea interactiva es imprescindible comunicarnos con un servicio 
que nos diga en el estado de la aplicación. Vamos a utilizar la arquitectura cliente
servidor desarrollando una API que nos permita interactuar con nuestra BBDD e implementar
lógica de negocio. 

En vez de utilizar los métodos nativos de node para crear un servidor http, utilizaremos
la librería de npm \verb*|express| que nos ofrece una API más amigable para el desarrollador.

Se han implementado los siguientes endpoints:

\begin{verbatim}
	1 GET  /crosswords
	2 GET  /crosswords/AAAA-MM-DD
	3 POST /crosswords/AAAA-MM-DD/solution
	4 POST /hint
\end{verbatim}

\subsubsection{Listar crucigramas}

Para listas todos los crucigramas que hay en la BBDD hay que hacer una llamada
HTTP de tipo GET al endpoint \verb*|/crosswords|.

Si tiene algún cliente HTTP como \verb*|curl| puede ejecutar el siguiente
comando:

\begin{verbatim}
	curl localhost:3000/crosswords
\end{verbatim}

La petición devuelve un JSON con la siguiente forma:

\begin{verbatim}
	[
		{
			"date": "2024-06-24T00:00:00.000Z",
			"numRows": 6,
			"numCols": 6,
			"numWords": 12,
			"numWordsAcross": 6,
			"numWordsDown": 6
		},
		...
	]
\end{verbatim}

\subsubsection{Obtener detalles de un crucigrama}

Para consultar una crucigrama por su fecha de publicación simplemente tiene
que hacer una llamada tipo GET al endpoint \verb*|/crosswords/AAAA-MM-DD|,
donde las 4 A es el año, las 2 M es el mes con dos dígitos (enero sería
01 no 1) y la DD es el día con dos dígitos (el 1 sería el 01).

Si tiene algún cliente de HTTP puede ejecutar le siguiente comando:

\begin{verbatim}
	curl localhost:3000/crosswords/2024-06-24
\end{verbatim}

Devuelve la siguiente respuesta:

\begin{verbatim}
	{
		"xword": {
			"_id": "667ebd00e6de693fc48b98a7",
			"date": "2024-06-24T00:00:00.000Z",
			"numRows": 6,
			"numCols": 6,
			"numWords": 12,
			"numWordsAcross": 6,
			"numWordsDown": 6,
			"clues": {
				"across": [...],
				"down": [...]
			},
			"crossword": [...]
		
	}
\end{verbatim}

\subsubsection{Comprobar solución del crucigrama}

Para comprobar si el crucigrama que ha hecho el usuario es correcto, el
usuario envía su solución al servidor al endpoint de tipo POST
\verb*|/crosswords/AAAA-MM-DD/solution|.

Para comprobar nuestra solución tenemos que enviar en el cuerpo
de la petición un JSON con este esquema:

\begin{verbatim}
	{
		"solution": <formato solución>
	}
\end{verbatim}

Se tiene que escribir una palabra formada por la concatenación
de los caracteres solución de las celdas.
El carácter que representa a un bloque es un punto.

Si tenemos el crucigrama solucionado:

\begin{verbatim}
	CBD -----> CBD
	B.. -----> CBD, B..
	D.. -----> CDB, B.., D..
	
	Solución: CBDB..D..
\end{verbatim}

Si tiene un cliente HTTP puede enviar el siguiente comando al servidor.
Cuidado 

\begin{verbatim}
	curl -X POST localhost:3000/crosswords/2024-06-24/solution
	-H "Content-Type: application/json; charset=utf-8"
	-d '{ "solution": "CBDB..D.." }'
\end{verbatim}

Si soluciona el crucigrama obtiene la siguiente respuesta:

\begin{verbatim}
	{
		"message": "¡Felicidades!, has solucionado el crucigrama"
	}
\end{verbatim}

Si se ha equivocado obtiene el siguiente mensaje:

\begin{verbatim}
	{
		"type": "wrong-answer",
		"title": "Solución incorrecta",
		"detail": "Parece que te has equivocado en alguna palabra.
		 Deberías revisar las pistas e intentarlo de nuevo",
	}
\end{verbatim}

\subsubsection{Buscar palabras en el diccionario}

Para buscar palabras en el diccionario se hacer una llamada HTTP
de tipo POST al endopoint \verb*|/hint| con el siguiente esquema
JSON:

\begin{verbatim}
	{
		"from": 0
		"word": "??aco"
	}
\end{verbatim}

Puede poner los siguientes caracteres en la búsqueda:

\begin{itemize}
	\item Cualquier letra de la \textit{a} a la \textit{z}, tildes
	incluidas.
	\item \textbf{?} es un comodín, cualquier letra coincide con
	este símbolo
	\item \textbf{*} es un símbolo que coincide con una secuencia de cero o más caracteres
	cualesquiera.
\end{itemize}

Pude mezclar estos caracteres para hacer búsquedas más complejas:

\begin{itemize}
	\item La búsqueda \textbf{??aco} encuentra registros que terminen en
		\textbf{aco} (ábaco, ataco, braco, etc...)
	\item La búsqueda \textbf{ab*} encuentra
	palabras que empiecen por ab y terminen en cualquier caracter
	(aborrascaban, aborrascado, aborrascais, etc...).
\end{itemize}


Elasticsearch devuelven paginados los resultados, cada página contiene
10 elementos. Si quiere obtener más resultados tiene que cambiar el \textit{offset} o la posición en el cuerpo de la petición.

La siguiente búsqueda tiene 178 resultados:

\begin{verbatim}
	curl -X POST -H "Content-Type: application/json" \
	-d '{ "from": 10, "word": "?aco"}' \
	http://localhost:3000/hint
\end{verbatim} 

\begin{verbatim}
	{
		"count": 178,
		"matched": [
			"ábaco",
			"abarraco",
			"abellaco",
			"abraco",
			"achaco",
			"afrodisíaco",
			"ajiaco",
			"alaraco",
			"alexifármaco",
			"amáraco"
		]
	}
\end{verbatim}

\subsection{Elastichsearch}

En la etapa de análisis del problema, encontré un video \cite{video:CreateXword}
interesante donde mostraban una buscador de palabras en inglés, \cite{OneLook}. Este buscador
lo utilizan mucho los crucigramistas de referencia para crear las pistas. Sirviendo 
de inspiración esta herramienta se ha implementado un buscador de palabras en español.

Es muy conocido ElasticSeacrh en la industria por ser tecnología muy eficiente para buscar
patrones en grandes cantidades de texto. Por lo que en el contexto del proyecto tiene sentido
usar ElasticSearch como motor de búsqueda. De hecho el stack de ElastichSearch utiliza Apache
Lucene otro buscador motor de búsqueda.

Para hacer las consultas a ElastichSearch se utilizará su API RESTful mediante el cliente
de Javascript \verb*|@elastic/elasticsearch| en el servidor de Express.

La siguiente consulta busca en el diccionario palabras que tengan en la segunda y en
la cuarta posición una a:

\begin{verbatim}
	curl -X GET "localhost:9200/words/_search?pretty" \
	-H 'Content-Type: application/json' -d'
	{
		"query": {
			"wildcard": {
				"word": {
					"value": "?a?a"
				}
			}
		},
	}
\end{verbatim}

Utilizando la API de javascript sería de la siguiente forma:

\begin{verbatim}
	elasticSearch.search({
		index: "words",
		query: {
			wildcard: {
				word: "?a?a",
			},
		},
	})
\end{verbatim}

Podemos ver que la API de javascript es una forma más programática de hacer la consulta.
Sin embargo sigue siendo un cliente de la API proporcionando una fachada al programador.

\subsection{Prerequisitos}

\begin{itemize}
	\item NodeJS 20.X.X o superior (https://nodejs.org/en/)
	\item Docker Desktop (Windows, https://www.docker.com/products/docker-desktop/),
	Docker Engine (Linux, https://docs.docker.com/engine/install/)
\end{itemize}

Para arrancar tanto el frontend como el backend se necesita alguna distribución
de NodeJS instalada. Para arrancar el backend hay que seguir los siguientes pasos:

\begin{verbatim}
Antes de arrancar el back necesita que el driver de mongodb para
express se conecte a una instancia en el ordenador,
si utiliza docker:
> docker run --name xword -p 27017:27017 -d mongo:latest

Una vez arrancada la BBDD puede arrancar el backend
	
Sitúese en la capeta back
> cd back
> npm install
> npm build  # Crea una carpeta dist en el que se encontrarán
los archivos .js requeridos para ejecutar el servidor de express

Después de arrancar mongo ya está en condiciones para arrancar
el servidor de express
> node dist/index.js
\end{verbatim}

Para arrancar el frontend tiene que situarse en la carpeta front y ejecutar

\begin{verbatim}
> cd front
> npm install
> npm run dev
\end{verbatim}

\subsection{Script}

El script tiene los siguientes parámetros posicionales:

\begin{itemize}
	\item Número de filas
	\item Número de columnas
	\item Ruta del archivo donde se encuentra la cuadrícula con el formato
	\ref{fig:xwordCustomFormat} esperado.
\end{itemize}

Para ejecutar el script primero tendrá que hacer los siguientes pasos:

\begin{verbatim}
	> cd back
	> npm install (Opcional si ya ha instalado los node_modules)
	> npm build (Se crea un carpeta dist con script.js)
\end{verbatim}

Ejemplo de uso:

\begin{verbatim}
	Windows:
	> node dist\script.js 11 11 --grid=.\crossword\example.txt
	Linux:
	> node ./dist/script.js 11 11 --grid=./crossword/example.txt
\end{verbatim}
